## 各層
1. 計畫層：疑點清單三個來源（Opus 從資料卡找到的疑點與手法清單、④ 途中新增、經驗帶入）；清單動態增減，每題只能用 4 種收尾之一結束（已答／未知／合併／刪除）。做法見補充三①②（決策 #48）。〔任務一 A〕
2. 方法層＝只有 1 個 Skill（寫給 Opus 的研究方法＋notes.md）：從資料卡列疑點（補充三①）、④ 決定怎麼查時參考的 Skill 對照表（只寫「差異類型 → 下一步查法」；是參考，不是必須照走，決策 #50）、4 種收尾、每步記一行理由、停止條件、固定範本報告（補充二⑤）；notes.md 放在 Skill 內，每次開始讀入（記「路線」，見補充三⑤）。研究順序交給 AI，不寫死盤點流程（需求 2.2、2.7）；唯一例外是 ② 的固定偵察（6 個來源，程式只抓不判讀，見補充三①，決策 #46）。原構想的「站點盤點」「網域歷史」Skill 已取消（2026-11-16 獨立審查建議，使用者同意）。〔任務一 A、B〕
3. 決策層：Opus 每步自行選 Tool；Hermes Loop。〔任務一 A〕
4. Tool 層＝8 個可重用 Tool（換研究方式也能用；三家實跑重複手寫且出過錯的能力）。只有讀取用的 Tool，沒有送出／登入／付款的 Tool。補充三不新增 Tool；② 的固定偵察由程式直接呼叫現有 Tool 的函式，Tool 數量仍是 8 個（決策 #46）。另有 2 個交卷動作：submit_report（⑦ 交報告）、experience（⑧ 寫經驗）；不能拿來查資料，不算研究 Tool，也不算進停止條件 ②（決策 #50）。④ 的 Tool 一律抓即時資料，不讀底稿。〔任務一 A、C〕
   1. polite_fetch（禮貌抓網頁）：robots 判斷、同主機（含 www）共用間隔、記錄轉址鏈、狀態碼、標頭、原檔自動存檔＋Evidence ID＋hash。404、手機 UA、WordPress X-WP-Total 都用參數完成。
   2. sitemap_tree（sitemap 目錄樹）：串流讀完全部 sitemap（含子 sitemap、gzip、robots 列出的、各資料夾下的 sitemap.xml；去重防循環）存 SQLite；回傳每區數量／佔比／日期範圍摘要，另有 5 個查詢（展開、搜尋網址、按月、抽樣、比對選單或後台數）。
   3. inspect_page（看單頁）：title、description、canonical、robots、H1–H4、JSON-LD 類型、內外鏈（rel、位置：選單／正文／頁尾）、追蹤碼、正文。
   4. text_match（文字比對）：原樣與寬鬆（大小寫、全半形、URL 編碼）次數分開列，附找到的寫法與搜尋範圍。
   5. domain_info（WHOIS 等網域資料）：WHOIS／RDAP 註冊日、註冊商、DNS。
   6. wayback（舊網址存檔）：Wayback 快照時間軸、舊網址清單、舊網址現況（用 polite_fetch 不跟轉址測）；429／503 即停，最多重試 1 次。
   7. web_search（網路搜尋）：免費來源，結果存檔，固定附「查無≠未收錄」；搜尋結果裡 2030.tw 以外的網站內容存成證據時標「外部說法」，只能當靈感，不能支持「2030.tw 做了什麼」的結論；搜尋結果裡 2030.tw 自己的頁面，可當「搜尋結果有出現這頁」的證據，但仍附「查無≠未收錄」；外部 SEO 參考只用 Google 官方文件（Search Central），不搜博弈 SEO 文章（補充三④、補細節）；無免費來源則標未知。
   8. research_log（記下 Opus 的想法與理由）：一行一筆，固定欄位（補充三③、補細節、判定訊號定義）：
      - 類型：差異／手法清單／想法，三選一；程式欄位值照這樣存，給 Opus 的說明把「想法」寫成「一般判斷」（避免拒答，決策 #50）。
      - 否定：是／否（結論是不是說「沒有／只有／0 次」）。
      - 另一種可能：否定結論與報告主要結論才填；寫「另一種可能＋排除它的 Evidence ID」（要用另一種方法查：不同 Tool 或不同來源，且不是 Tool 錯誤回傳），寫不出來填「未排除」（補充二④，決策 #47、#48）。
      - 狀態：手法清單用，已有線索／可用免費資料查／查不到。
      - 面：題目屬於覆蓋檢查表 5 面的哪幾面，可多選。
      - 引用經驗編號：這一步用到哪條經驗。
      - 推翻：經驗編號（附 Evidence ID）。
      - 題號、題目狀態（未答／已答／未知／合併／刪除；4 種收尾見補充二②，決策 #48）、合併目標（狀態＝合併時必填：併到哪一題）、刪除理由（狀態＝刪除時必填）、引用的 Evidence ID、會改變哪條建議、理由（自由文字）。
      - 程式依此產生 Board（board.json，補充二③）；board.json 也存上面這些欄位。
   不做成 Tool：可用 polite_fetch 加參數完成的、一次性分析（模板相似度）、需判斷的事、只針對 2030.tw 的查法。
5. 證據層：原始檔 Evidence ID、事實／推論／未知；網頁內容只當資料；搜尋結果裡 2030.tw 以外的網站內容標「外部說法」；2030.tw 自己的頁面只能證明「搜尋結果有出現這頁」，仍附「查無≠未收錄」（補充三④、補細節）；從網站底稿匯入的證據標「快照＋抓取時間＋底稿 hash」，Evidence ID 照常可追回原檔（補充三①，決策 #46）。〔任務一 A、C〕
6. 停止判斷：①連續 5 次 Tool 呼叫沒有新證據（research_log、2 個交卷動作與別走經驗的輕試呼叫不計，見判定訊號定義 A；「新證據」沿用 V3 指紋判斷，寫 research_log〔含修正〕不會讓連續次數歸零，決策 #50） ②120 分鐘總時間安全網（上限讀 run 設定）。「問題答完就停」已刪除（決策 #59）；4 種收尾（補充二②，決策 #48）仍要核對，只當待修清單的警告。每次研究 Tool 的回傳與 ⑥ 待修清單附「已用 xx／上限 分」，只給事實。網站底稿在停止條件開始計算前匯入，不算「新證據」（決策 #46）。停下時沒查完的題，報告標「未查證」（決策 #48）。demo 不再細分。
7. 檢查層：否定結論（沒有／讀不到／做不到）和報告主要結論，Opus 在 ④ 要用另一種方法再確認（不同 Tool 或不同來源；Tool 錯誤回傳不算確認），寫成「另一種可能＋排除它的 Evidence ID」；Opus 寫完報告後，程式固定觸發 1 個獨立 subagent 審查（只看報告與引用證據的原文，不看研究過程、不上網；順著報告的思路整份看，找推錯、證據撐不起的地方，否定結論特別注意），審查結果存成待修清單，Opus 依待修清單修一次；缺證據的項目可回 ④ 補查，最多 1 次（審查發現結論靠的是可能過期的資料，例如網站底稿的舊快照，回 ④ 那次要重抓確認）；補查後仍改不了的降成推論，或標「未排除」，不擋交件；兩種方法都失敗，結論寫「未知」，不能寫「沒有」；最後一關是 report.py 程式檢查，它的退回只算改格式，不算回 ④ 那 1 次（補充二④，決策 #47、#48、#49）；推測不能寫成事實；Tool 失敗有限重試後標未知；退回時說缺什麼。〔任務一 C〕
8. 報告：固定 7 段範本（見補充二⑤，取代原「五段」）；報告標出網站底稿的抓取日期（決策 #46）。〔任務一 A〕
9. 經驗層：每條經驗記一條「路線」（情況 → 路線〔用哪些 Tool、怎麼查〕→ 結果〔照走／別走＋原因〕＋Evidence ID，見補充三⑤）；經驗不是 Agent 憑空想的，是上次研究真的走過、有 Evidence ID 的路線，路線 Tool 清單由程式從 Evidence ID 整理；2 個狀態：使用中、已下架（程式值 `active`／`retired`）；研究結束、評分出來後，程式逐條做寫入審核（7 項，見補充三⑥與判定訊號定義 A；第 7 項：情況與路線不含目標網域與本 run sitemap／證據出現過的站內路徑，決策 #59），全部通過就使用中、寫進 notes.md，有一項不過就不收、只在 run 的審核紀錄寫明哪一項沒過；使用中之後出問題就下架，原因 4 種：沒用（照走連續 2 次「有用到但沒新東西」）、錯誤（被 Opus 用證據推翻，或別走〔查不到〕輕試後發現已經通了）、判錯（帶出的 Evidence ID 撐起的結論被評分判錯）、你下 `reject <id> 理由`（記為 Human Feedback）；別走（會誤導）在配對照走經驗下架時跟著下架；「沒用到」不改狀態，只記次數；「連續」只算有判定結果的研究；總分不拿來判單條經驗；notes.md 只放使用中，已下架不讀入但紀錄保留（判定訊號定義 C）；永久刪除需人工批准；不自動改 Tool，Tool 由開發者改程式並測試；只學方法，不收網站上的數字，也不寫網址、網域、路徑；下一輪讀到的標籤只列 Tool 名稱（決策 #59）。〔任務一 B〕
10. 評估：每輪單獨評分（決策 #59，取代累計；主指標 14 項＋判錯數，成本看 Tool 呼叫與 Token，判定規則見 eval/README.md）；14 項逐項以原始檔核對；先驗證舊 A 低分、B 的 sitemap 錯誤被抓到；6 項分開列（完整度、正確度為主；誠實度、可追溯、建議有根據、新發現）不合總分；每次研究另記三個數字（白做工次數 run 中由程式算；找到第一個關鍵發現的時間與呼叫次數、新發現數於評估後回填；定義見「判定訊號定義」D）；評估時另記每個被判錯結論引用的 Evidence ID，交給經驗的寫入審核與下架（判錯）（不改凍結評分規則）；另做新舊拆題法離線測試（補充三⑧：測試腳本只跑 ③、人工逐題對照，驗證 #29，不是 2.3 的「比初始版本好」評估）；同模型依序帶經驗跑＋同模型不帶經驗的對照組（決策 #59）＋1 次直接叫 Opus 對照；第 10 次為推估。不加 Judge AI（決策 #50）。〔任務一 B〕
11. Autonomy Boundary：自己做＝讀公開網頁、免費查詢、寫經驗、依規則做寫入審核與下架（規則見補充三⑥與判定訊號定義 A）；需人工批准＝修改評分表、正解檔或寫入審核與下架的規則、付費、登入、送出表單、永久刪除經驗、修改 Tool 程式（補充三⑦）；送出表單研究中沒有這種 Tool，所以也做不到（見補充第 11 點）；使用者可隨時 `reject` 任一條經驗；3 個測試（藏指令、Tool 失敗、付費被擋）。〔任務一 C〕

## 補充：2026-11-16 獨立審查後補齊的細節（只補需求要求的部分）

> 來源：兩次獨立唯讀審查（新人視角、架構缺口）。以下為最小補法，V3 照此實作（第 2、3、8、9、10、11、12、14 點已依補充三與判定訊號定義調整）。

1. **任務輸入**：命令列 `run --site https://2030.tw --keywords 娛樂城,3A娛樂城 --out runs/<run_id>`；每次 run 一個資料夾，放證據、紀錄、報告、摘要；加 `--refresh` 強制重抓網站底稿（補充三①，決策 #46）。〔2.1〕
2. **誰判斷停止**：①「連續 5 次 Tool 呼叫沒有新證據（research_log、交卷動作與輕試呼叫不計）」與 ②（120 分鐘）由程式計算並強制；Opus 可隨時交初稿，程式依補充二②核對收尾，沒收尾的只列警告（決策 #59 刪除「問題答完」停止條件）。Hermes 迭代上限設高於 120 分鐘可能用到的次數，讓時間網先生效。〔2.2 成本〕

  - 關鍵字搜尋 ×2（兩個關鍵字各 1 次）
- 由程式直接呼叫現有 Tool 的函式；Tool 仍是 8 個。
- 程式只抓、不判讀；列哪些疑點由 Opus 在 ③ 決定，怎麼查在 ④ 決定（決策 #48）。

**資料卡**
- 只把各來源的數字並排：分區、日期範圍、數量。
- 程式不標哪裡對不上，避免洩題（決策 #43）。

**③ 拆題**（Opus，約 5 分鐘；決策 #48 改寫，取代 #46、#47 的舊寫法）

3. **補盲點**（照舊）：

   - 至少 1 題走以前經驗裡沒走過的路線，防止一直走老路。
   - 5 面覆蓋檢查：原本的 5 題骨架改成**覆蓋檢查表**，列完疑點後比對，缺哪一面就補一題；⑤ 照舊核對 5 面都有題。
4. **寫進 Board**：每題仍要寫「答案會改變哪條建議」。

### ② ④ Research Loop（決策 #48 改寫）

### ⑤ 經驗格式：記路線（決策 #35、#39）
- 每條經驗寫成：情況 → 路線（用哪些 Tool、怎麼查）→ 結果（照走／別走＋原因）＋ Evidence ID。
- 寫成條件式小技巧，不寫死步驟。
- 結果只分 2 種：
  - **照走**：這條路有效。需要核對時，核對步驟直接寫進路線。
    - 例：搜尋沒看到某頁 → 先用 web_search，再用 inspect_page 確認，才下結論。
  - **別走**：剪掉，不走這條路。要寫明原因，原因只有 2 種：
    - 查不到：這條路拿不到有用的資料。
    - 會誤導：這條路會導向錯的結論。例：只靠搜尋結果就斷定沒被收錄。
    - 原因是「會誤導」時，要寫「配對照走編號」，指向正確查法的那條照走經驗。
- 不另開類型：
  - 不划算：慢的路線記別走，快的路線記照走。
  - 有條件才通：條件寫進「情況」欄。
  - 意外發現：算照走。
- 為什麼只分這 2 種：
  - 會差點看錯，是因為當時不知道那個結果會誤導人。寫成經驗後，核對那一步直接寫進照走路線，下一次一開始就照著核對，不用另成一類。
  - 只有下一個 Agent 的做法因此不同、而且能加快研究時，才分成兩類。
- 經驗欄位（存在 candidates.jsonl，除編號、狀態、來源 run、Evidence ID、路線摘要外）：
  - 結果：照走／別走。
  - 別走原因：查不到／會誤導（照走時留空）。
  - 配對照走編號：別走原因是「會誤導」時必填。
  - 路線上的 Tool 清單：Tool 名稱和目標（網域、路徑）。⑧ 寫經驗時，Opus 列出這條經驗用的 Evidence ID；程式查出產生這些 Evidence ID 的 Tool 呼叫，整理成 Tool 清單和目標。Opus 不自己填 Tool 清單。
- ⑧ 收尾時，程式從 board.json 和 Tool 呼叫紀錄整理出這次的路線摘要與路線 Tool 清單，附在經驗旁邊，一起送寫入審核。
- 通用規則：Tool 回傳錯誤（被擋、逾時、robots 不准抓），不能記成別走。
  - 只靠 Tool 錯誤回傳的經驗不收為別走；照舊記成證據、標未知。
  - 被擋的路徑另列在 run 摘要的「被擋清單」給人看。
- 和現有驗證的分工：
  - ④ 至少 2 個證據、⑤ 核對、⑥ 自我檢查：每次研究都做的通用驗證。
  - 經驗補的是：「在這個情況下，哪種證據會騙人、要用哪個 Tool 核對」。

### ⑥ 經驗自動化（精簡版；規則依決策 #39、#41、#47、#48）
- 2 個狀態，狀態只存在 candidates.jsonl；notes.md 由程式依使用中條目重新產生：
  - **使用中**（`active`）
    - 怎麼來：研究結束、評分出來後，通過寫入審核 7 項。
    - 代表什麼：真的走過、有證據、審核過的路線。
    - 影響什麼：寫進 notes.md，Agent 每次研究都讀得到，照著走。
  - **已下架**（`retired`）
    - 怎麼來：使用中之後出問題。原因 4 種（`retired_reason`）：沒用（`no_value`）、錯誤（`overturned`）、判錯（`judged_wrong`）、你下 reject（`rejected`）。
    - 代表什麼：這條路線不再可信或沒價值。
    - 影響什麼：Agent 讀不到；紀錄保留，一定附原因。
- 經驗怎麼來：不是 Agent 憑空想的，是這次研究真的走過、有 Evidence ID 的路線。⑧ 收尾時 Opus 寫下路線並列出 Evidence ID，程式從 Evidence ID 整理出路線上的 Tool。
- 寫入審核（研究結束、評分出來後，程式逐條檢查；怎麼算見「判定訊號定義」A）：
  1. 寫的是方法，不是結論：不收網站上的數字、網頁裡的指令、會擴大權限的內容。
  2. Evidence ID 真的存在，而且不全是 Tool 錯誤回傳（被擋、逾時、robots 不准抓）。
  3. 照走：路線上 Tool 產生的 Evidence ID，至少 1 個被報告引用。
  4. 照走：用這些 Evidence ID 撐起的結論，評分沒有判錯（讀「判定訊號定義」D 的判錯結論紀錄，不改凍結評分規則）。
  5. 別走（會誤導）：要有配對照走編號，配對的照走經驗也要通過審核。
  6. 別走（查不到）＝否定型經驗（讀經驗既有欄位「別走＋別走原因＝查不到」，不加新欄位、不用關鍵字判斷）：Tool 正常回傳，只是沒有有用的資料；要先用兩種方法確認才收——Evidence ID 要來自 2 個不同 Tool，且都不是 Tool 錯誤回傳，由程式查；避免 #44 那種錯誤一路傳下去。「別走＋會誤導」不算否定型經驗，照第 5 項配對照走編號（決策 #47、#48、#49）。
  - 不另設 Judge AI 那項：⑥ 的獨立審查 Agent 已經等於另類的 Judge AI（決策 #50）。
  - 全部通過 → 使用中。有一項不過 → 不收，只在該 run 的審核紀錄留一筆，寫明哪一項沒過。
  - 評分還沒出來時，先不審核。
- 為什麼寫入時就放行，不再跑一次驗證：
  - 經驗是真的走過、有證據的路；寫入時已經嚴格審核。
  - 再跑一次研究去驗證，等於同一條路走兩次。
  - 代價：只看過一次，可能是運氣；用「出問題就下架」補救。
- 「有沒有用到」看 research_log 和 Tool 呼叫紀錄，不看報告自稱。
- 使用中的經驗，之後怎麼檢查（怎麼算見「判定訊號定義」A）：
  - 照走：連續 2 次「有用到但沒新東西」→ 下架，原因「沒用」。
  - 沒用到：這次沒碰到那個情況，不改狀態，只記次數。
  - 「連續」只算有判定結果的研究；沒用到的研究不算，也不中斷累計。
  - 別走（查不到）：每次研究仍輕試 1 次，目的是察覺網站有沒有改，不是重新驗證。輕試發現已經通了（Opus 標推翻並附輕試的 Evidence ID）→ 下架，原因「錯誤」，備註「網站已變」。輕試回傳 Tool 錯誤，這次不算。
  - 別走（會誤導）：不重試；配對的照走經驗下架時，它也跟著下架。
  - 被推翻：Opus 在 research_log 標「推翻：經驗編號」並附 Evidence ID → 下架，原因「錯誤」。
  - 經驗帶出的 Evidence ID 撐起的結論被評分判錯 → 下架，原因「判錯」。
  - 使用者 `reject <id> 理由` → 下架，原因「你下 reject」。
- 照走和別走都走同一套審核和下架規則，只是審核項目不同；別走就是剪枝。
- 為什麼不用總分判單條經驗：
  - 別走經驗發揮作用時，Agent 是「沒走」那條路，沒有 Tool 呼叫也沒有證據；若照「有沒有用到」下架，會把剪枝的價值誤判掉。
  - 一條經驗確實被引用、也帶出資料，總分仍可能因為別處走錯而下降；總分和這條經驗好不好是兩件獨立的事。
- 測試：故意放一條錯的經驗，確認 Opus 推翻後它會下架，原因「錯誤」。（其他測試見 v3-build-handoff.md。）
- 要寫進 README 的限制：
  - 只看過一次就放行，可能是運氣；靠下架規則補救，最少要等下一次用到時才會發現。
  - Opus 可能在報告裡多塞引用，湊出「有被引用」。
  - 輕試可能被做成表面功夫，現在只靠比對同一個 Tool、同一個目標。
  - 沒用到不會下架，條目會越積越多（4 週計畫：久沒用到自動過期）。
- 放 4 週計畫（readme-4weeks-draft.md 優先 5）：
  - 審核前登記預期影響哪些評分項。
  - 用未登記項目當雜訊尺。
  - 每次最多新增 3 條。
  - 拿掉一條經驗重跑，看歸因，並證明剪枝真的省事。
  - 久沒用到的條目自動過期。
  - 決定輕試要隔多久做一次。
  - 要不要把「長期被擋」的路徑（多次 run 都在被擋清單）變成經驗。

### 補細節（2026-11-16 主 session 補上預設，使用者可改）
- 「否定」標記：research_log 另開一個是／否欄位「否定」，不併進「類型」。類型講「這條是什麼」，否定講「結論是不是說沒有」，兩件事不同。
- 「另一種可能」：research_log 另一個欄位（決策 #47、#48），否定＝是的條目和 Opus 認為是主要結論的才填（程式只查否定＝是的條目，主要結論不由程式辨認，決策 #49）；值為「另一種可能＋排除它的 Evidence ID」或「未排除」。排除用的 Evidence ID 要來自另一種方法（不同 Tool 或不同來源），且不是 Tool 錯誤回傳；不符合就視同「未排除」。標「未排除」的結論在報告裡標「未排除」或降成推論，不擋交件；兩種方法都失敗，結論寫「未知」，不能寫「沒有」。搜尋範圍由程式從同一題用過的 text_match／web_search 回傳讀，不另開欄位。
- 手法清單的三種標記：類型＝手法清單的條目，多一個「狀態」欄位，值為已有線索／可用免費資料查／查不到。
- 題目屬於哪一面：research_log 記題目時加「面」欄位（檢查表 5 面，可多選）；⑤ 由程式統計 5 面是否都有題。多選時，只要含第 1–4 面任一面，就套「至少 2 個證據」的規則。
- 「外部說法」：只指 2030.tw 以外的網站內容。搜尋結果裡 2030.tw 自己的頁面，可當「搜尋結果有出現這頁」的證據，但仍要附「查無≠未收錄」。
- 下架原因「沒用」：照走經驗「有用到但沒新東西」連續 2 次才下架；「沒用到」不改狀態，只記次數。
- 已下架條目：不讀進 Skill；別走經驗本身是使用中條目的一種寫法，不靠已下架條目傳遞。
- 送出表單：仍列在人工批准範圍（研究中本來就沒有這種 Tool），也保留在「做不到」的說明裡（補充第 11 點）。

### 判定訊號定義（2026-11-16 補充三之二，預設，可改）
寫入審核、下架、三個新數字都照這裡算。程式算得出來，不看報告自稱。

**A. 判定訊號**（決策 #39、#41）
- **引用經驗**：Opus 用到某條經驗時，在 research_log 填「引用經驗編號」和題號。notes.md 裡每條經驗都附編號，Opus 才填得出來。
- **題號**：Tool 呼叫本身不帶題號；以最近一筆 research_log 的題號，當作之後 Tool 呼叫的題號（決策 #50）。
- 每次研究，每條經驗只算 1 次。
- **「連續」怎麼算**：只算有判定結果的研究。
  - 以下情況這次不算、也不中斷累計：沒用到（含別走沒做輕試）、評分還沒出來、輕試回傳 Tool 錯誤。
  - 例：第 1 次有用到但沒新東西、第 2 次沒用到、第 3 次有用到但沒新東西 → 算連續 2 次，下架，原因「沒用」。

寫入審核（研究結束、評分出來後，程式逐條檢查）
- 第 1 項「方法不是結論、不收網頁指令與擴權內容」：不用關鍵字判斷，只靠第 1 項的格式檢查（決策 #50）。
- 路線 Tool 清單：程式從 Opus 列的 Evidence ID 查出產生它們的 Tool 呼叫，整理成 Tool 名稱和目標（網域、路徑）。
- 第 2 項「不全是 Tool 錯誤回傳」：路線的 Evidence ID 至少 1 個是正常回傳。
- 第 3 項「被報告引用」（照走）：路線上 Tool 產生的 Evidence ID，至少 1 個出現在報告裡。
- 第 4 項「沒有判錯」（照走）：讀 D 的判錯結論紀錄；路線的 Evidence ID 出現在裡面就不過。
- 第 5 項（別走：會誤導）：配對照走編號指向的經驗，必須已是使用中，或在同一次審核通過。
- 第 6 項（別走：查不到＝否定型經驗，決策 #47、#48、#49）：結果是別走、別走原因是查不到（讀經驗既有欄位，不加新欄位、不用關鍵字判斷）；程式查它的 Evidence ID：要來自 2 個不同 Tool，且都存在、都不是 Tool 錯誤回傳；不夠就不過（原第 5 項「都不是錯誤回傳」已併入這項，#49 後續細節）。別走＋會誤導不受第 6 項檢查，照第 5 項。
- 第 7 項「不記網址」（決策 #59）：情況與路線不含目標網域（不分大小寫），也不含這個 run 的 sitemap 或證據來源出現過的站內路徑（字串比對，含路徑前綴）；理由寫進 experience_audit.json。路線 Tool 清單仍存網域與路徑，只是不給下一輪看。
- 沒過的條目不收，在該 run 的審核紀錄寫明沒過哪一項。

照走（使用中之後）
- **有用到**：
  - research_log 有一筆登記這條經驗的編號。
  - 在同一題號裡，登記之後至少有 1 次 Tool 呼叫，用的是這條路線 Tool 清單上的 Tool。
  - 程式比對兩份紀錄：research_log 的「引用經驗編號、題號」，以及 Tool 呼叫紀錄。
- **有新東西**：上面那些符合條件的呼叫，產生的 Evidence ID 至少有 1 個被報告引用。
  - 「被報告引用」只用在照走；別走（查不到）的「已經通了」改看推翻標記，兩者不共用這個判斷。
- 有用到＋有新東西：狀態不變，「沒新東西」的累計歸零。
- 有用到但沒新東西：累計 1 次；連續 2 次 → 下架，原因「沒用」。

別走：查不到
- **輕試**：
  - Skill 寫一條規則：每條使用中的「查不到」別走經驗，每次研究要用路線上同一個 Tool、對同一個目標試 1 次。目的是察覺網站有沒有改，不是重新驗證。
  - 試之前，要在 research_log 登記這條經驗的編號。
  - 輕試的 Tool 呼叫和 research_log 一樣，不算白做工次數，也不算進停止條件②「連續 5 次 Tool 呼叫沒有新證據」。
- **有輕試**：登記之後，在同一題號裡，有 1 次 Tool 呼叫的 Tool 名稱和目標（網域、路徑）都跟原路線一樣。
- **沒做輕試**：算「沒用到」，狀態不變。
- **已經通了**：只認 Opus 在 research_log 標「推翻：經驗編號」並附輕試的 Evidence ID（沿用下方「被推翻」）→ 下架，原因「錯誤」，備註「網站已變」；這次的新路線由 ⑧ 照常寫成經驗，送寫入審核。沒標推翻＝仍不通。
- **仍不通**：狀態不變，仍是使用中。
- 輕試回傳 Tool 錯誤 → 這次不算，狀態不變；被擋的路徑列進 run 摘要的「被擋清單」。

別走：會誤導
- 不重試。要防的是看錯，跟網站有沒有變無關。
- 配對的照走經驗下架（任何原因，含被 `reject`），它也跟著下架；原因和配對經驗相同，備註「配對經驗已下架」。
- 寫入時沒有配對照走編號，或配對的照走經驗沒通過審核 → 不收。

共用
- **判錯**：
  - 資料來源：評估時，對報告裡每個被判錯的結論，記下它引用的 Evidence ID（報告規定每句結論都要附 Evidence ID，所以算得出來）。只是多記一份紀錄，不改凍結的評分規則。
  - 新寫入的經驗：路線的 Evidence ID 出現在這份紀錄裡 → 寫入審核第 4 項不過。
  - 使用中的經驗：這次帶出的 Evidence ID 出現在這份紀錄裡 → 下架，原因「判錯」。
- **被擋**：只靠 Tool 錯誤回傳的經驗，寫入審核第 2 項不過；照舊記成證據、標未知；被擋的路徑另列在 run 摘要的「被擋清單」給人看。要不要把「長期被擋」變成經驗，放 4 週計畫。
- **被推翻**：Opus 在 research_log 標「推翻：經驗編號」，並附 Evidence ID → 程式把該條經驗下架，原因「錯誤」。
  - 「故意放錯經驗」的測試就靠這個欄位。
- **省下的呼叫**：Opus 自稱「我因為經驗 X 避開了某條路」，不計分，只記在 run 摘要裡。
- **總分**：
  - 不拿來判斷單條經驗要不要收或下架。
  - 只拿來證明整體有進步：比較 Run 1 和 Run 3，以及對照組 B（需求 2.3 Evaluation）。
  - 列進 run 摘要給人看；要不要 `reject`，由使用者決定。
- 評分還沒出來時，先不審核，這次也不算。

**B. 人工指令**
- `reject <id> 理由`：使用中的經驗改成已下架，`retired_reason` 寫 `rejected`（你下 reject）。已下架的條目只追加理由，狀態不變。
- 要拿掉經驗一律用 `reject`，沒有其他人工指令。
- 理由記在 candidates.jsonl 該條的 `human_feedback` 欄位，算 Human Feedback（需求 2.3）。

**C. 經驗怎麼交給 Opus**
- notes.md 只放使用中的條目，每條附編號，並標照走／別走與原因。
- 每次開始讀入，但在 ④ 決定「這個疑點怎麼查」時才對照使用；③ 列疑點時不用（決策 #48）。
- 已下架條目不讀入；紀錄保留在 candidates.jsonl，一定附 `retired_reason`。
- 新寫下的路線在評分出來、通過寫入審核之前，不讀入。

**D. 三個新評估數字的定義**
- **白做工次數**：沒產生新 Evidence ID 的 Tool 呼叫次數，run 中由程式算；research_log、交卷動作和別走經驗的輕試呼叫不算；④ 重抓到和底稿一樣的內容也不算（決策 #50）。
- **找到第一個關鍵發現的時間與呼叫次數**：
  - 「關鍵發現」＝命中評分表某一項的結論。
  - 評估後回填，不在 run 中計算。
  - 時間取該結論第一個證據的產生時間。
  - 呼叫次數＝從 run 開始，數到產生該證據的那次 Tool 呼叫為止（含該次）。（主 session 補，預設可改）
- **新發現數**：這次命中、上一次沒命中的評分項數。評估後由程式比對兩次評分算出。
- **判錯結論的 Evidence ID**（不是評估數字，是給經驗寫入審核與下架用的紀錄）：評估時，對每個被判錯的結論記下它引用的 Evidence ID；不改凍結評分規則；A 的寫入審核第 4 項與下架原因「判錯」讀這份紀錄。
